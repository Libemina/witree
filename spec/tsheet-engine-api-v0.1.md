# tsheet-core エンジン API 仕様 v0.1

ステータス：ドラフト（MVP 対象） / 作成日：2026-09-17 / 関連：tsheet形式 仕様 v0.1（本体仕様）、View定義仕様 v0.1（View仕様）

## 1. 概要と原則

tsheet-core は、tsheet 形式のワークブックを読み込み、検証・計算・変更・射影・マージを行うエンジンである。Witree のデスクトップ／Web アプリ、CLI、Git マージドライバー、将来の MCP サーバーは、すべてこのエンジンを同じ API で呼び出す。契約は `engine/engine-api.v0.1.ts` の型定義であり、本書はその意味論を定める。

| 原則 | 内容 |
|---|---|
| 純粋 | I/O・時計・乱数・ロケールを持たない。必要なものは `Host` として注入する。`lib: ES2022` のみでコンパイルできる |
| 決定的 | 同じ `Host` の応答と同じ入力に対して、常に同じ出力（`serialize()` は 1 バイトも違わない） |
| Op 単位 | すべての変更は自己完結した Op の列（トランザクション）として渡す。エンジンが状態を勝手に変えることはない |
| 責務の集中 | 検証・計算・射影（フィルタ・ソート・crosstab・書式判定）・逆操作の生成・マージはエンジンが行う。UI は表示と入力、Host はファイル・ロック・スナップショット・自動保存を担う |
| 非同期・Result 型 | 外部インターフェースはすべて `Promise` を返す。拒否・衝突・診断は戻り値で返し、例外はエンジン内部の不整合にのみ使う |

## 2. 構成

```
UI（React）  ──メッセージ──▶  Worker: tsheet-core  ◀── Host（TS 側アダプタ）──▶ Rust / FS API
CLI（Node）  ──直接呼び出し──▶  tsheet-core          ◀── Host（Node fs）
```

`Host` は次を提供する（§3）。ストレージはエンジンの外にあり、エンジンは `PartMap`（論理パス → テキスト）を受け取り、返すだけである。Worker とのやり取りは §12 のメッセージ形式に従う。CLI はプロセス内で同じインターフェースを直接呼ぶ。

## 3. Host

| メンバー | 内容 |
|---|---|
| `clock.today()` / `clock.timezone` | `TODAY()` の基準。`settings.timezone` があればそちらを優先する |
| `ids.newId()` | UUIDv4。エンジンは自動生成する Op（削除に伴う参照解除など）で使う |
| `hash(bytes)` | 同期のハッシュ関数。`contentHash()` と外部変更検出に使う。アルゴリズムは Host が選ぶが、同じワークブックを扱う Host 間で揃える（推奨 SHA-256） |
| `log?` | 診断のログ出力先 |

エンジン内で `Date`・`Math.random`・`Intl`・`setTimeout` を使ってはならない。これは `tsconfig` の `lib` 設定と lint で強制する。

## 4. ライフサイクル

| メソッド | 内容 |
|---|---|
| `load(parts)` | パートを解析し、スキーマの意味検証（S 系）、データの構造検証（D01〜D09、D19、D22）、実効値の計算、値の検証（D10〜D18、D20、D23）、View の検証（V 系）を行う。`readOnly` の条件は本体仕様 §12 に従う（S 系 error、schemaVersion 不一致、コンフリクトマーカー、単一ファイルの途切れ） |
| `serialize()` | 正規化済みの `PartMap` を返す（本体仕様 §11.1、View仕様 §10）。doc の本文、`params` を含む `workbook.json` も含む |
| `contentHash()` | `serialize()` 結果全体のハッシュ。Host は保存時にこれを記録し、外部変更の検出に使う |

`load` は何度でも呼べる。呼ぶたびに状態を置き換える（reconcile の結果を採用する場合など）。

## 5. Op とトランザクション

### 5.1 5 系統

| 系統 | 対象 | 備考 |
|---|---|---|
| `DataOp` | ノードの作成・削除・移動・値・doc 本文 | `set` の `null` は「明示的な空」、`unset` は「未設定に戻す」（本体仕様 §7） |
| `SchemaOp` | 型・フィールド・子ルール・制約・列挙・settings | `renameField` / `renameType` は存在しない（§6.4） |
| `ViewOp` | View 定義の作成・削除・部分更新・置換 | `patch` は JSON Pointer 相当のパスで 1 箇所を更新する |
| `MarksOp` | 手動書式のレコード単位・セル単位の設定 | `null` で削除 |
| `ParamOp` | ルートノードのフィールド値 | `DataOp` の `set` / `unset` と同じ意味論 |

### 5.2 自己完結性

Op は「選択中の行の下」「最後の兄弟の後ろ」のような相対指定を持たない。`create` と `move` の `order` は呼び出し側が `orderBetween(a, b)` で求めて渡し、`create` の `id` は `newId()` で採番して渡す。これにより、同じ Op の列をどの環境で再生しても同じ結果になり、Undo・スナップショット比較・将来の CRDT 化に共通の基盤ができる。

### 5.3 トランザクション

`Transaction` は Op の列と呼び出し側が採番した `id`、任意の `label` を持つ。**全体で成功か失敗か（all-or-nothing）** であり、いずれかの Op が拒否（§6.1）されれば何も適用せず、`ok: false` で拒否理由を返す。Undo の単位もトランザクションである。

`preview(tx)` は `apply(tx)` と同じ結果を返すが状態を変えない。破壊的なスキーマ変更や大量の貼り付けの前に、UI が件数や診断を提示するために使う。

## 6. 適用の規則

### 6.1 拒否と受理

構造が壊れる Op は拒否し、値の違反は受理して診断で返す（本体仕様「データを壊さない」の原則）。利用者が一時的に違反状態（複製直後の unique 重複など）を経由して編集できるようにするためである。

| 拒否（`ok: false`、エラーコード E 系） | 受理して診断（D 系・V 系） |
|---|---|
| E01 存在しない親・型・フィールド・View | D10 型・format・制約違反 |
| E02 親子の循環（`move` が自分の子孫を親にする） | D11 required の実効値が空 |
| E03 その親の下に置けない型 | D12 unique 違反 |
| E04 `cardinality: "one"` の 2 件目の作成、`required` の子の単独削除 | D13 checks 違反 |
| E05 `onDelete: "restrict"` の ref に参照されているノードの削除 | D14 ref の参照先が存在しない（参照先の削除後に残るのは E05 で防ぐが、外部変更で起こりうる） |
| E06 計算フィールド（rollup / formula）への `set`（`whenNoSource: "input"` の入力可能な状態を除く） | D17 子があるため入力値が無視される |
| E07 予約語・不正な識別子・型名 `Root` の定義 | V 系（View の参照切れは受理し、View を開けない状態として報告） |
| E08 `id` の重複作成、存在しないノードへの操作 | |
| E09 `schemaVersion` 不一致・読み取り専用状態での変更 | |
| E10 doc 以外への `setDoc`、doc への `set` | |

### 6.2 値の正規化

`set` の値は本体仕様 §6 の保存形式に正規化してから格納する（空文字 → `null`、format ごとの表記、decimal の桁数、配列の順序）。正規化できない値（型が違う、パースできない）は **拒否せず** 、文字列のまま保持して D10 を返す。UI は D10 のあるセルを強調表示する。

### 6.3 delete の意味論

- 対象ノードとその **子孫をすべて削除** する。
- 削除範囲のノードを参照する `onDelete: "clear"` の ref について、参照を消す `set` Op を自動生成し、`expanded` に含める。`restrict` の参照が削除範囲の外に 1 つでもあれば E05。
- 削除範囲のノードに紐づく **すべての View の marks（レコード単位・セル単位）** を削除する `MarksOp` を自動生成する。
- doc の本文パートも削除対象とする（`parts` に含めて Host に通知する）。
- `required` かつ `cardinality: "one"` の子は単独では削除できない（親ごと削除する）。

### 6.4 SchemaOp

- **フィールド ID と型名は不変** とする。`renameField` / `renameType` は提供しない。利用者に見せる名称は `label` であり、業務上の ID が必要なら通常のフィールド（`code` など）として定義する。これにより、データ・View・marks・式の書き換えが最も広範囲に及ぶ変更を仕様から排除する。
- `removeType`：その型のノード（子孫を含む）の削除 Op、他の型の `children` からの除去、ref の `target` からの除去、View の列・rules からの除去を自動生成する。
- `removeField`：全ノードの該当値の除去、View の列・sort・filter・rules・marks からの除去、式の参照切れの検出（S07 として拒否）を行う。
- `updateField` で `type` を変える場合：各ノードの値を新しい型へ変換する `set` Op を自動生成する。変換できない値は `null` にせず **元の文字列のまま保持** し（D10）、`report.unconvertibleValues` に列挙する。
- `updateField` で制約を強めた場合：既存データは書き換えず、診断（D10〜D13）が増える。`preview` で件数を確認できる。
- 互換性のない変更（型の削除、フィールドの削除・型変更、子ルールの削除、列挙値の削除）を含むトランザクションは `schemaVersion` を 1 増やし、`dataSchemaVersion` も同時に更新する。それ以外（label、追加、制約の緩和・強化、settings）は変えない。

### 6.5 逆操作（Undo）

`apply` の結果には、同じ状態に戻す `inverse` トランザクションが含まれる。エンジンは自動生成した Op（参照解除、marks 削除、スキーマ変更に伴う書き換え）も含めて逆操作を作る。`delete` の逆は削除したサブツリー・doc・marks の再作成である。逆操作の `id`・`order`・値はすべて元の値を保持する。

履歴（Undo / Redo スタック）は Host が保持する（セッション内。Q8 の決定）。外部変更を取り込んだ後（§10）も履歴は保持し、対象ノードが存在しなくなった Op は `apply` 時に E08 で拒否されるため、Host はそのトランザクションを飛ばして次の履歴に進み、利用者に通知する。

## 7. 計算

### 7.1 実効値

各ノードの各フィールドについて、`stored` → `inherited` → `rollup` / `formula` → `default-input`（`whenNoSource: "input"` の入力値）→ `empty` の順で `source` を決め、`NodeView.effective` に値と由来（継承元 `from`）を返す。UI は `source` を使って継承値・計算値の見た目を変える。

### 7.2 再計算

MVP は **全体再計算＋メモ化** とする。`apply` のたびに、依存グラフ（本体仕様 §8.4）上でトポロジカル順に評価し直し、前回の結果と比較して `ChangeSet.effective` を作る。静的な依存グラフは S08 の循環検出に必要なので常に保持する。差分再計算への切り替えは内部実装の変更にとどめ、API は変えない。

### 7.3 変更通知

`ChangeSet` は 2 段で返す。`records`（保存形式が変わったもの）は Undo・reconcile・保存の要否判定に、`effective`（実効値が変わったセル）は再描画に使う。Worker からは `apply` の戻り値に加えて `changes` イベントでも通知する。表示中の射影の更新は、UI が `project()` を再度呼ぶ（`ProjectionOptions.range` で表示範囲だけを取る）。

## 8. 問い合わせと射影

`project(view, opts)` は View 仕様の処理順序（`tree.types` → `filter` → `sort` → 書式）を適用し、`Projection` を返す。

- `rows` は表示順で、折りたたみは反映しない。折りたたみは個人状態なので、UI が `opts.collapsed` に渡すと、その子孫を除いた行だけを返す。
- `cells` のキーは列の `field`（`$title` などの特殊列を含む）、crosstab では列のキー値、行合計は `$rowTotal`。
- `CellView.editable` は、計算フィールド・継承のみ・読み取り専用列・crosstab の 2 件以上のセル・View の `readOnly` をすべて考慮した最終判定である。UI は独自に判定しない。
- `CellView.style` は marks と rules を View 仕様 §8.3 の順で合成した結果である。
- crosstab の空セルへの入力は、UI が `create`（`parent` = 行、`key` = 列の値、`value` = 入力値）を組み立てて `apply` する。エンジンはそのために `Projection.columns` にキー値を返す。

`search` は簡易検索（タイトル・文字列フィールドの部分一致、任意の式）で、フィルタ入力の補助やジャンプに使う。

## 9. 式 API と入力ガード

`parseExpr` は構文・参照・型を検証して `ExprInfo`（結果型、参照するフィールド、使用関数）を返す。rules・checks・filter・formula を UI で編集するときの即時検証に使う。`evaluate` は任意のノードを文脈に式を評価し、数式バーのプレビューや検証ルールの試験に使う。

式は副作用も I/O も持たない宣言的な言語であり、外部へのアクセス経路はない。したがってリスクは **サービス拒否（過大な計算）** に限られる。エンジンは、UI から渡された式にも、ファイルから読み込んだ式（他者が作ったワークブック）にも、同じ制限を課す。

| 制限（`ExprLimits`） | 既定 |
|---|---|
| 式の長さ | 4,096 文字 |
| 構文木の深さ | 64 |
| 1 回の評価の演算ステップ数 | 100,000 |
| 正規表現のパターン長 | 512 文字（`pattern`・`REGEXMATCH`） |
| 文字列演算の結果長 | 65,536 文字 |

制限を超えた場合は評価を打ち切り、結果を空として D10 相当の診断（`E20`）を返す。正規表現は ECMAScript の構文に限定し（本体仕様 §10.2）、バックトラックの爆発を避けるため、ネストした量指定子（`(a+)+` など）を `parseExpr` で拒否する。`evaluate` は `adhoc` 目的として扱い、結果を保存せず、状態を変えない。

## 10. reconcile（3 方向マージ）

### 10.1 入力と出力

`reconcile(base, disk, { unsaved })` は、「最後に読み込んだ／保存した内容（base）」「現在のエンジン状態（local）」「ディスク上の新しい内容（disk）」を比較し、マージ結果 `merged`・衝突一覧・変更差分を返す。状態は変えない。Host は、衝突がなければ `load(merged)` で採用し、衝突があれば UI に解決を求めて `resolve()` を呼ぶ。同じ関数を Git マージドライバー（CLI `merge`）で使う。CLI では未解決の衝突があれば終了コード 1 でファイルを書き換えない。

### 10.2 データの規則（レコード単位 → フィールド単位）

| base / local / disk の状態 | 結果 |
|---|---|
| 片方だけが変更（作成・削除・移動・値） | その変更を採用 |
| 両方が同じ値に変更、両方が削除 | 採用 |
| 同じフィールドを異なる値に変更 | 衝突 `field` |
| 片方が削除、片方が同じノード（または子孫）を編集 | 衝突 `deleteEdit` |
| 両方が `move` し、合成すると循環する | 衝突 `moveCycle` |
| 両方が `move`（循環しない） | disk を採用し、`notes` で通知 |
| 両方が同じ親の下で `order` を変更 | disk を採用し、`notes` で通知（並び順は破壊的でない） |
| doc 本文を両方が変更 | 衝突 `doc`（行単位の自動マージは v0.1 では行わない） |
| 一方が `set`、他方が `unset` | 衝突 `field`（`undefined` を値として扱う） |

「未設定」と `null` は区別して比較する。比較は保存形式の値で行い、実効値は使わない。

### 10.3 View・marks・params

View 定義は JSON のキー単位（`columns` は `field` をキー、`rules` は `id` をキー、その他はパス）、marks はレコード ID・フィールド ID をキーとして同じ規則でマージする。params はデータのフィールドと同じ規則に従う。

### 10.4 スキーマの外部変更

スキーマはフィールド単位のマージが意味を持たないため、**disk のスキーマを正とし、local の未保存トランザクション（`unsaved`）を disk の状態に対して順に再適用する**。各トランザクションは通常の規則（§6.1）で受理または拒否され、結果は `schemaReplay` に返る。拒否されたのは、削除された型・フィールドへの操作など、新しいスキーマでは成立しない変更である。これにより、外部でスキーマが変わっても、成立する未保存の編集は失われない。

再適用のために、Host は「最後の保存以降に適用したトランザクション」を保持しておく必要がある（Undo 履歴と同じものを使える）。

### 10.5 解決

`resolve(resolutions)` は各衝突について `local` / `disk` のいずれか、または `field` 衝突には任意の値を指定する。すべての衝突が解決されるまで、Host は保存を止める（本体仕様 D22 と同じ扱い）。解決は通常のトランザクションとして適用され、Undo できる。

## 11. 差分と形式変換

- `diff(a, b)` は 2 つの `PartMap` をレコード単位で比較し、作成・削除・移動・更新の一覧と変わったパートを返す。スナップショットの比較・復元、CLI の `diff` コマンドに使う。
- `pack` / `unpack` は本体仕様 §2.2 の変換で、`load` 不要の純粋関数である。`unpack` は D21（構造不正）を返しうる。

## 12. Worker メッセージ

| 種別 | 形式 |
|---|---|
| 要求 | `{ id, method, params }`。`method` は `Engine` のメソッド名、`params` は引数の配列 |
| 応答 | `{ id, result }` または `{ id, error: { code, message, data } }`。`error` はエンジン内部エラー（例外相当）にのみ使い、拒否や衝突は `result` の `Result` 型で返す |
| イベント | `changes`（`apply` / `resolve` 後）、`diagnostics`（診断の増減）、`progress`（`load` や大規模な `apply` の進捗） |

要求は到着順に直列で処理する。`project` のような読み取りも `apply` と同じキューに入るため、UI は「apply の応答を待ってから project を呼ぶ」だけで整合が取れる。大きな `PartMap` の受け渡しは、Worker の構造化クローンのコストを避けるため、文字列は `Transferable`（`ArrayBuffer`）で渡してよい。

## 13. エラーコード（E 系）

| コード | 内容 |
|---|---|
| E01〜E10 | §6.1 の拒否理由 |
| E11 | トランザクションの `id` が重複している（二重送信） |
| E12 | `resolve` に未知の衝突、または衝突が残っている状態での保存要求 |
| E13 | `load` されていない状態でのメソッド呼び出し |
| E20 | 式の評価が制限（§9）を超えた |
| E21 | 内部不整合（バグ）。`error` として返す唯一の種類 |

## 14. バージョニングと決定性の保証

- エンジンのパッケージは semver で管理し、`version()` で `{ engine, spec }` を返す。API の破壊的変更はメジャーバージョンで示す。仕様の `specVersion` とは独立に進める。
- 型定義から JSON Schema（Op・Transaction・Message 用）を生成し、CLI の入力検証と MCP サーバーのスキーマに使う。
- CI では、Node.js とブラウザ（Vitest ブラウザモード）の両方で同じ `PartMap` を `load` → `serialize` し、`contentHash()` が一致することを確認する（ゴールデンテスト）。トランザクションの適用と `inverse` の適用で元に戻ることも同様に検証する。

## 15. MVP の対象外
